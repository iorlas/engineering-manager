# Report spec

Output: one file `em-metrics/<date>/report.html`. Offline: no CDN, no external fonts, no network calls (corporate machines often block them). Inline CSS, inline SVG charts generated by a Python script (`scripts/build_report.py`) from `derived/metrics.json`. Light and dark both readable (`prefers-color-scheme`). No JS required; use `<details>` for expanding. Readable at phone width.

Numbers are rendered by the script from `metrics.json`. Insight text is written by you after reading `metrics.json`, saved to `derived/insights.json` (`{section_id: [{kind, text, cites:[metric_id], n}]}`), and merged into the HTML by the script. Never type a number that is not in `metrics.json`.

## Sections, in this order
1. **Header**: scope (repos, Jira projects), checkpoint windows with dates, data caveats in 3 lines max.
2. **Summary** (open by default): a table, rows = headline metrics, columns = the three checkpoints + change arrow. Headline metrics: deploy frequency, lead time, change failure rate, time to restore, PR cycle time, unreviewed share, AI share. Cells show value and `n`; `low_n` greyed; proxies tagged "proxy". Below it, 3-5 findings as Observed / Likely / Unknown bullets.
3. **Bottlenecks** (open): stacked bar per checkpoint of the four PR stages (coding, pickup, review, approval to merge) in median days; the dominant stage named. Jira status-dwell bars per checkpoint when Jira exists. One paragraph: where time is lost and what that suggests checking next.
4. **AI adoption** (open): AI share per checkpoint (bar), AI vs non-AI comparison table with `n`, the correlation-not-causation line, and the "not measurable, here is how to make it measurable" note when no markers were found.
5. **DORA** (collapsed): one small chart per metric (checkpoint bars plus weekly sparkline), one short insight each, proxy labels, definition link text taken from `metric-definitions.md`.
6. **PR flow** (collapsed): throughput, size, review rounds, unreviewed share; per metric chart + insight.
7. **QA and Jira flow** (collapsed, only with Jira): qa_wait, bounce_back_rate, reopen_rate, bug_ratio, bug_escape, wip.
8. **Per engineer** (collapsed, only if enabled): table of authors with n; banner "context for conversation, not ranking"; no sorting by speed (sort by name or id).
9. **Method and caveats** (collapsed): data sources, deploy and incident proxies used, windows, exclusions, extraction counts, what was not measured, run date.

## Chart rules
- Same axis range across checkpoints within a metric. Zero baseline for bars.
- Label values directly on bars; no legend hunting. One colour per stage, consistent everywhere. Colour is never the only signal (add text labels).
- Titles state the metric and unit. Charts with `low_n` points draw them hollow.
- Weekly sparklines highlight the three windows as shaded bands.

## Insight rules
- Every insight: kind (Observed | Likely | Unknown), 1-2 sentences, the metric id it cites, its `n`.
- No insight from `low_n` data, except as Unknown.
- Say "coincides with" for anything linking AI use to an outcome.
- Name concrete next checks ("look at the 12 PRs over 500 lines in repo X"), not generic advice.
- Per-engineer insights, if any, are about the team pattern (for example review load concentrated on two people), never about an individual's speed.

## Done-check
Open the file path in the reply; also verify by script that it has no `http://` or `https://` resource references other than text, every section id appears, and every number in the summary table equals its `metrics.json` value.
